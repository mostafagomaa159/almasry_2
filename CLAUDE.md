`almasry_2` — a Flutter (Dart SDK ^3.10.8) e-commerce/pharmacy app for Al Masry Pharmacy, backed by a Magento REST API. Arabic-first (RTL) with English fallback.

## Architecture

### The `part` / barrel-file convention (most important thing to know)

Every feature under `lib/features/<feature>/` has a barrel file `<feature>_imports.dart` (e.g. `login_imports.dart`, `home_imports.dart`). That barrel holds **all** the imports for the feature and a list of `part` directives. Each view, view_model, and widget file begins with `part of '../<feature>_imports.dart';` and contains **no imports of its own**.

Consequences when editing:
- To use a new symbol inside a view/widget/view_model, add the `import` to the feature's `_imports.dart`, not to the file you're editing.
- To add a new file to a feature, create it as a `part of`, then register a `part '...'` line in the barrel. A file not listed in the barrel will not compile as part of the feature.
- Cross-feature use works by importing the *other feature's barrel* (e.g. `home_imports.dart` imports `product_list_imports.dart`).
- **A `part` file belongs to exactly one library.** So anything two features both need cannot be a `part` — it has to be a standalone library (its own imports, no `part of`) that both barrels `import`. That is why the shared state models (`CartModel`, `FavoriteProductModel`), the shared args (`OtpVerificationArgs`, `OrderDetailsArgs`, `AddressFormArgs`, `OrderConfirmedArgs`), the shared services (`AuthSessionService`, `AppStartupService`, `FavoritesService`, `CartService`, `AddressBookService`) and the shared widgets (`AuthHeader`, `OrderStatusChip`, `CartTotalsCard`, `CheckoutStepper`) all live in `lib/core/` as plain libraries.
- **No barrel imports another barrel.** A symbol two features both need belongs in `core` instead. `cart` and `checkout` are the case that keeps testing this rule, and the answer has settled on routing rather than imports: they are two sibling routes, so neither library needs the other's Views. An earlier design had checkout host the cart as page 0 of its `PageView`, which forced `checkout_imports.dart` to import `cart_imports.dart`; that is gone. Don't bring it back — if a feature seems to need another feature's widget, the question is whether it should be a route of its own.
- Some files live outside the feature folder but are still `part of` its barrel — response models under `lib/core/models/response/...` that only one feature reads, plus `lib/features/layout/view/layout_shell_view.dart` which is `part of` `home_imports.dart`.

### One feature per screen, with a per-screen ViewModel

**Every feature follows this** — login, register, otp_verification, splash, wishlist, my_order_details, orders, categories, product_list, edit_profile, profile, product_details, home, checkout, order_confirmed, address_form. (`login`, `register` and `otp_verification` are three separate features; there is no `auth` feature. `cart` and `checkout` are two features and two routes: `cart` is the shell's cart tab, and `checkout` is a top-level route holding the three-step pager in **one** View file and **one** `CheckoutViewModel`. The old `checkout_flow` / `checkout_shipping` / `checkout_payment` / `checkout_review` folders are gone, folded into `checkout`.) In each:

- The **View** holds only lifecycle and layout: `vm._init()` in `initState`, `vm._dispose()` in `dispose` where the VM has one, and a widget tree. No validation, no API calls, no prefs, no navigation.
- The **ViewModel** is per-screen, constructed by the View (`final LoginViewModel vm = LoginViewModel();`) and owns the controllers, focus nodes, validation, persistence and navigation. Its members are **private** (`_emailOrPhoneController`, `_submitRegularLogin`), which works because the View and widgets are `part of` the same barrel.
- **Widgets take a single `vm` param** — `RegularLoginForm(vm: vm)` — and read `vm._data`, `vm._passwordController`, `vm._togglePasswordVisibility` directly instead of receiving a dozen constructor arguments.
- View-local *layout* state stays in the View as `setState` (e.g. which login form is visible, the OTP pin rebuild that enables the verify button). Only business logic belongs in the VM.

- A ViewModel has a `_dispose()` **only when it has something to release** — controllers, timers, focus nodes, its own cubits — and the View calls it from `dispose`. A VM with nothing to release has no `_dispose()` at all and its View has no `dispose` override — `OrderConfirmedViewModel` is the remaining example. `CartViewModel` has none either. `CheckoutViewModel` does have one, and it releases exactly one thing: the flow's `PageController`. Neither VM closes its cubits; those go with the discarded VM. Don't add an empty one back.

Cross-screen state does **not** live in a feature. It goes in a locator-registered service under `lib/core/services/` — `AuthSessionService`, `AppStartupService`, `UserProfileService`, `FavoritesService`, `CartService`, `AddressBookService`. Their members are public precisely because several feature libraries consume them; per-screen ViewModel members are private.

`CartViewModel` is the clearest example of the split running *the other way* — state a screen deliberately does **not** own. The cart is app-global (the bottom-bar badge, every product card's add button and and all three checkout steps read it), so `CartService` owns it and the VM is a thin adapter: `_cartCubit` is a `late final` onto the service and `_incrementQuantity` / `_decrementQuantity` / `_removeItem` / `_refreshCart` are one-line calls into it. Nothing about the basket is stored on the VM. Its only other member is `_navToCheckout`, which guards on a non-empty cart and then does `_navService.pushNamed(RouteNames.checkout)` — cart knows the checkout *route*, not the checkout feature.

Two deliberate exceptions to "private members":
- A member nothing reads yet stays public, because privatising it would only produce an `unused_element` / `unused_field` warning (`OrdersViewModel.fetchMore`/`reset`, `CategoriesViewModel.errorMessage`, `HomeViewModel.changeOfferTab`).
- Genuinely presentational leaf widgets keep their parameters — `AppTextField`, `EditProfileTextField`, `ProfileMenuItem`, `OtpVerifyButton`, `ProductDetailsSummarySection`. The *section* widget above them takes `vm`.

### State management: `GenericCubit<T>` (no per-feature blocs)

There are no feature-specific Bloc events/states. Everything uses:

- `GenericCubit<T>` (`lib/core/base/bloc/generic_cubit.dart`) — a `Cubit<GenericState<T>>` with one method, `onUpdateData(T data)`.
- `GenericState<T>` (`Equatable`) carries `data` plus a `changed` bool that `onUpdateData` flips each emit, so identical data still triggers a rebuild.

A ViewModel is a **plain class** (not a Cubit) that owns **one `GenericCubit<T>` per thing the UI watches**, plus plain fields for everything nothing rebuilds on by itself. `BrandsViewModel` is the reference shape: `_brandsCubit` / `_totalItemsCubit` / `_showFAB` / `_currentIndex` / `_clearSearchCubit` / `_loadingCubit` alongside a plain `_errorMessage`, `_page`, `_allBrands`.

**There is no `copyWith` anywhere in the project, and no per-feature state data class.** Both are gone on purpose — `UserModel`, `CartData`, `FavoritesModel`, `ProductListData`, `SplashData`, `ProfileData`, `HomeModel`, `EditProfileModel` and `OrderDetailsModel` have all been dissolved into cubits and plain fields. Don't reintroduce either: a screen that needs a new piece of state gets its own small cubit, or a plain field if nothing paints from it. (The only `copyWith` calls you'll see are the framework's, e.g. `TextStyle.copyWith`.)

Two idioms carry the weight that a data class used to:
- **Plain field + a repaint emit.** A value nothing watches on its own lives in a plain field, and the cubit that *is* watched emits so the widget re-reads it. `OrderDetailsViewModel._fail` sets `_errorMessage` then emits `_orderCubit`; `AuthSessionService.validationCubit` does the same for `emailOrPhoneError` / `passwordError` / `otpError` / `authErrorMessage`; `CartService._handleFailure` re-emits the unchanged cart for the same reason (the `changed` flag makes that work).
- **One cubit over a values-arrive-together payload.** Where a whole block of state lands in a single response, one cubit carries it so the page can't paint half of it — `HomeViewModel._structureCubit` (`GenericCubit<_HomeStructure?>`, everything the CMS reply fills in) with `_productsLoadingCubit` flipping false as the section products land into plain lists. Such a payload class is constructed whole from the response, never copied.

Services follow the same shape. `AuthSessionService` is the fullest example: `passwordHiddenCubit` / `rememberMeCubit` / `loadingCubit` / `phoneAuthLoadingCubit` / `otpLoadingCubit` / `otpCountdownCubit` alongside `validationCubit`, whose emit is what repaints the plain `emailOrPhoneError` / `passwordError` / `otpError` / `authErrorMessage` fields a form reads.

Note that `GenericState<T>` itself *is* `Equatable`, which is what makes the `changed` flag necessary.

Views consume the cubit two ways, both in use:
- `BlocBuilder<GenericCubit<T>, GenericState<T>>(bloc: viewModel.xCubit, ...)` — for locally-created ViewModels (e.g. `home_view.dart`).
- `BlocProvider<GenericCubit<T>>.value(value: viewModel.xCubit, child: BlocBuilder<...>)` — e.g. `profile_view.dart` (over its `_languageCodeCubit`), and `home_view.dart` for the favourites cubit its product cards read. `main.dart` provides nothing; every other `BlocBuilder` names its cubit with an explicit `bloc:`.

### Dependency injection (`get_it`)

`lib/core/base/locator/locator.dart` exposes `sl` and registers **every** service as a lazy singleton: `SharedPrefsServices`, `DbServices`, `NetworkLoggerService`, `ApiLoggerInterceptorService`, `ApiService`, `GraphQLService`, `NavigationService`, `AuthSessionService`, `AppStartupService`, `UserProfileService`, `FavoritesService`, `CartService`, `AddressBookService`, `AlertService`, `CacheManagerService`, `PushNotificationService`. No service is reached any other way — no hand-rolled `X.instance`, no `const X()` held as a field. Consumers hold a locator field (`final _dbService = sl<DbServices>();`) and services compose through the locator too, which is why `ApiLoggerInterceptorService` takes its `NetworkLoggerService` from `sl` in the registration. The service-owned cubits hold **app-global** state; consumers reach them with an explicit `bloc:` on the `BlocBuilder` (e.g. `bloc: sl<CartService>().cartCubit` in `LayoutShellView`, whose badge paints `state.data.totalQuantity`) rather than through a provider.

**No ViewModel is registered in the locator** — every feature's view constructs its own in `initState()` (`final HomeViewModel vm = HomeViewModel();` then `vm._init();`) and disposes it. Global state belongs in a `core/services` singleton, per-screen state does not.

### Routing (`go_router`)

`lib/core/routing/app_router.dart` defines a single static `GoRouter`. `app_routes.dart` holds two constant classes: `AppRoutes` (paths, used only in the router's `path:` fields) and `RouteNames` (names, used in the router's `name:` fields and at every call site).

**All navigation goes through `NavigationService` — no `context.go` / `context.push` / `Navigator` anywhere in `lib/`.** Get it with `sl<NavigationService>()`: a `final NavigationService _nav = sl<NavigationService>();` field in `State` classes and ViewModels, or a `NavigationService get _nav => sl<NavigationService>();` getter in `StatelessWidget`s (a field would break their `const` constructors). It wraps the router (`goNamed` / `pushNamed` / `pushNamedAndReturn` / `replaceNamed` / `pop` / `canPop`) so ViewModels can navigate with no `BuildContext`.

Always pass a `RouteNames` constant, never an `AppRoutes` path — the two are easy to confuse and both are `String`. Passing a path to `goNamed` throws at runtime, and pushing a raw path fails for shell-nested screens whose real location differs from their `AppRoutes` constant (`orderDetails` actually lives at `/profile/orderDetails`, `productDetails` at `/home/productDetails`).

Structure: `splash` → `login` / `otpVerification` / `signup` sit outside the shell, each coming from its own barrel (`login_imports.dart`, `otp_verification_imports.dart`, `register_imports.dart`). `addressForm` also sits outside the shell, so the form covers the bar and a save returns to the step that opened it. **There are no `checkoutShipping` / `checkoutPayment` / `checkoutReview` routes any more** — those three constants are gone from `AppRoutes` and `RouteNames`, and nothing navigates to a checkout step. The whole cart-to-order cycle is one route, `cart`, rendering `CheckoutView`.

A `StatefulShellRoute.indexedStack` wraps four branches — home, categories, cart, profile — rendered inside `LayoutShellView`, which drives `HomeBottomNavBar` via `navigationShell.goBranch`. Nested routes (`productList`, `productDetails` under home; `orders`, `orderDetails`, `wishlist`, `editProfile` under profile; `orderConfirmed` under cart) keep the bottom bar visible. **Nothing hides the bar, and nothing needs to.** `LayoutShellView`'s `bottomNavigationBar` is a single `BlocBuilder` on `sl<CartService>().cartCubit` for the badge and knows nothing about checkout: the design's bar-free checkout comes from `checkout` being a top-level route *outside* the shell, so the bar is not in the tree at all. That is also the whole reason the flow needs no service — see the checkout bullets.

Arguments are passed as `state.extra` and cast to typed `*Args` models under `lib/core/models/response/*/..._args_model.dart`. Casts are unguarded (`state.extra as ProductListArgs`), so a navigation missing `extra` crashes — always pass it.

**One exception: a route with children must type-test rather than cast.** go_router hands the *same* `extra` to every route in the matched chain, so `goNamed` straight to a nested route also rebuilds its parents with that child's argument. `home` and `profile` therefore do `extra is ProfileArgs ? extra : null` — `/profile/orders` takes a `String` email and `/home/comingSoon` takes a `String` title, and a plain cast in the parent throws `type 'String' is not a subtype of type 'ProfileArgs?'`. (`pushNamed` from inside the parent hides this, because the parent is already mounted and never rebuilt.)

### Networking

`ApiService` is a thin Dio wrapper (`get` / `post`) over `ApiConstants.baseUrl`, with the Magento bearer token and 20s timeouts set on `BaseOptions`. There is **no repository/data layer** — each ViewModel (or `AuthSessionService`, for auth) calls `_apiService` directly, maps the raw JSON into models itself, and owns its own `_extractApiMessage(DioException)` helper (duplicated across them). Endpoints and the token are hardcoded in `lib/core/constants/app_api.dart`; `mediaBaseUrl` is used to build image URLs.

Auth is only half-wired: `AuthSessionService.login()` and `register()` are **stubs** — `await Future.delayed(AppDurations.authStub)` with no API call, so they can never fail. Only the phone path is real (`startPhoneAuth` → `_forgetPassword`, `verifyOtpCode` → `_activateAccount` + `_loginAfterOtp`). Don't treat email/password login as functional; the Magento login endpoint isn't in `app_api.dart` yet. All three flows still open a session (`AppStartupService.saveLoggedIn()`) and write what they know to `UserProfileService` — a stubbed sign-up that left the new account a guest with no stored name was the bug that made the profile screen look empty.

**The two phone endpoints disagree about the mobile's format.** `/auth/forget-password` takes `identity` and accepts the E.164 form `_normalizePhone` produces (`+201…`) — that call is what sends the SMS, and it works. `/auth-after-otp` takes `mobile` and answers `The provided mobile number is not valid` for the same string, so it matches against the mobile as Magento stored it (the local `01…` the customer registered with). `startPhoneAuth` therefore keeps **both** forms — `verificationPhone` (normalized, used for forget-password and resend) and `verificationLocalPhone` (as typed) — and `verifyOtpCode` walks `_mobileCandidates()` (local, then normalized, then normalized without the `+`) until one reply carries a token. Only a failure costs an extra request, so a store that wants the normalized form still works. `RegisterCustomerOtpModel.message` exists so a 200-with-no-token surfaces the API's own words instead of the generic `otpLoginFailed`.

**`activate-account` takes the same treatment, for the same reason.** `verifyOtpCode` used to pass the forget-password `code` as `ActivateAccountRequest.customerId`, but `RegisterCustomerModel` carries `activation_code` and `customer.id` as *separate* fields, so a code is not an id. `_customerIdFrom` now digs a real id out of the forget-password reply (`customer_id` / `customerId` / `customer.id` / `id`, first non-empty non-zero wins) and `_activationCandidates` tries that before falling back to the code. A store whose reply carries no id, or whose endpoint really does want the code, behaves exactly as before.

Both loops are deliberately **additive**: each keeps today's value as its last candidate, so neither can turn a working call into a failing one, and the extra request only happens after a failure. They also capture a `DioException` per attempt instead of letting the first one abort the flow, which is what previously turned a format mismatch into a dead end. If the debug log shows which candidate actually wins, collapse the list to that one.

The phone path is also the only one that produces a **customer session**: `_saveOtpSession` persists the phone, the `customer.email` the reply carries, and Magento's customer token (`PrefKeys.customerToken`), then calls `AppStartupService.saveLoggedIn()` and `adoptCustomerCart()`. The email/password stub sets `isLoggedIn` but has no token, so those users stay on a guest cart. `AppStartupService.logout()` is what takes the token and the cart back off the device.

**`UserProfileService` owns the customer's own details** (`firstName` / `lastName` / `email` / `phone` / `gender` / `birthDate` / `hasPregnancy` / `chronicDisease` / `diseaseType`), because Magento exposes no "get customer" call here and the OTP reply carries only the token, the customer id and the email — never a name. So the profile is whatever the sign-up form and the edit screen collected, read straight off shared preferences the way `cartId()` is. Its `save()` treats `null` as "leave alone" and `''` as "clear", which is what lets sign-up write four fields, the OTP reply two, and the edit screen all nine including the ones just emptied. `AppStartupService.logout()` is the only caller of `clear()`; no screen writes those keys itself. `ProfileViewModel` prefers the stored value and falls back to `ProfileArgs`, and takes its guest/account decision from `isSignedIn` rather than the args — the guest flag rides to `home` as `extra`, so a later tap on the Profile tab arrives with none.

`GraphQLService` is the equivalent wrapper for GraphQL (`query` / `mutate`), holding one long-lived `GraphQLClient` for the whole app session. Every call carries `Authorization: Bearer <PrefKeys.customerToken>` once a customer token is stored — that header is the whole difference between a guest cart and a customer one. A reply whose message reads as an auth failure drops the stored token (`_forgetTokenIfRejected`), because a token Magento no longer accepts would otherwise break browsing too, with no way back. **Both methods deliberately bypass the normalized cache** (`FetchPolicy.noCache`) — do not "upgrade" that to `networkOnly`. It looks equivalent (both always hit the network) but hands back a *re-read* of the normalized cache, and because the client is shared, two queries selecting the same entity with different field sets make that re-read fail with `CacheMissException: Round trip cache re-read failed`. The cart hit this: `getCartDetails` selects `Cart.id` and stores a `shipping_addresses` list with no `available_shipping_methods`, then `getCartShippingMethods` selects `cart` without `id` and its re-read resolves back to that stored entity. Nothing in the app reads the cache, so there is nothing to gain by re-enabling it.

`errorMessageFrom` is the one place that turns a caught error into copy. It rejects anything implausible as a *message* — empty, over 240 characters, or starting with `<` — because both wrappers fall back to stringifying the underlying exception, which can be an HTML error page or a whole request dump. Discarded text goes to `debugPrint`, so a mystery failure is still diagnosable from the console.

Request DTOs live in `lib/core/models/request/`, responses in `lib/core/models/response/`, both hand-written `fromJson` / `toJson` (no codegen).

### Cart & checkout (GraphQL)

The whole basket-to-order flow is GraphQL — documents in `app_graphql.dart`, no REST involved.

- **`GraphQLDocuments.cartFragment`** is the shape `getCartDetails` and *every* cart mutation select. So one round trip both applies a change and refreshes the state, and `CartModel.fromResponse(json, mutationKey: 'addSimpleProductsToCart')` parses them all — that factory unwraps the mutation envelope and hands `CartModel.fromJson` the cart itself, which is the split the two names carry. Add a field to the fragment, not to one operation.
- **`CartService` owns the cart; there is no `cart_actions.dart` and no `CartCountService`.** One locator-registered service in `lib/core/services/cart_service.dart` holds the whole basket: a `cartCubit` (`GenericCubit<CartModel>`), a `loadingCubit`, the masked cart id (`PrefKeys.cartId`), and every operation — `loadCart()` (also the refresh), `resolveCartId()` (never mints) / `ensureCartId()` (mints), `addToCart(sku:quantity:)`, `updateQuantity(item:quantity:)`, `removeItem(item)`, `adoptCustomerCart()`, `clearCart()` (logout, order placed, and a missing-cart reply all take the same path). The stateless `cart_actions.dart` function library and the badge-only `CartCountService` were both folded into it; nothing else in `lib/` reads `PrefKeys.cartId`.
- **The badge counts distinct products, not units.** `LayoutShellView` builds on `sl<CartService>().cartCubit` and paints `CartModel.productCount` (`items.length`), so two of one product read as 1 and one each of two products read as 2. `totalQuantity` — the sum of the line quantities — is still on the model and is what the API returns; nothing paints it today. Because the badge watches the cart itself, any screen's add, quantity change or removal moves it without a sync call, and splash primes it with `loadCart()`.
- **A ViewModel reaches a service-owned cubit through a `late final` field, never a pass-through getter.** `_cartCubit` and `_addressesCubit` are `late final` (the `late` is only because they read another instance field), because `cartCubit` / `addressesCubit` are `final` on their services and the reference never changes — re-resolving it on every read bought nothing. A getter is still right for anything *computed* (`CartModel.productCount`), and `_cart()` stays a method because the cart itself changes.
- **Every page paints the same cubit.** `CheckoutViewModel` and `CartViewModel` each hold `late final GenericCubit<CartModel> _cartCubit = _cartService.cartCubit;` and `CartModel _cart() => _cartService.cart;` — two references to one service-owned cubit, not two copies of a cart, so the cart page and the checkout pages always agree. A step that changes the cart server-side (setting an address, a carrier, a payment method) just calls `_cartService.loadCart()`, and the totals card, the review sections and the badge all repaint together. The earlier per-step copies fetched with a `fetchCart(id)` helper are gone, and so is that helper.
- **Every cart `BlocBuilder` has the same shape**, the cart screen's: an explicit `bloc: vm._cartCubit`, untyped builder params, `if (state is GenericUpdateState) { final cart = state.data; ... }` and a loading widget after it — `CartShimmer` on the cart page (in `CartView.build`), `CustomAppLoadingView` on the checkout pages. The guard matters because `cartCubit` starts in `GenericInitialState`; the cart is read once per page at the top of its tree and passed down as a plain `cart` param (`CartSummary(vm: vm, cart: cart)`, `CheckoutShippingSummary(vm: vm, cart: cart)`), never re-watched by the leaf that draws the totals.
- **The cart page keeps nothing.** `CartViewModel` reaches the basket only through `CartService`; because that cubit is app-global, the cart page repaints on an add made from home or product details no matter when it was last built. Owning the cart per-screen is what previously left that tab showing whatever it loaded on its first visit.
- **The cart screen never mints a cart.** `loadCart()` uses `resolveCartId()` — stored id, else `customerCart` when a customer token exists — and paints an empty cart when that yields nothing. `createEmptyCart` is reached only through `ensureCartId()`, i.e. by an add or by the shipping step. Minting an empty cart in order to render an empty cart was pointless work on every cold open of the tab.
- **A failed cart load is reported by an alert only.** `_handleFailure` shows `errorMessageFrom(error)` through `AlertService` and re-emits the unchanged cart so watchers repaint; there is no error state on the screen and no retry button — `CartView.build` has exactly three outcomes (shimmer before the first emit, `CartEmptyView`, the list), and a failed load with an empty cart lands on the empty view. An earlier `errorMessage` field plus `CustomAppErrorView` branch was removed deliberately; don't reintroduce them. A "could not find a cart" reply is the one failure that is *not* reported — it drops the id and empties the cart, or the app would be stuck on an unretryable error.
- **The quantity stepper has no busy state.** `_increment` / `_decrement` / `_removeItem` do not disable the row or show a spinner while their mutation is in flight, so rapid taps race: each builds its payload from the rendered `item.quantity`, and two taps before the first reply both send the same value. The `busyItemsCubit` that used to prevent this was removed deliberately.
- **Cart names line up on purpose.** A widget's class name matches its file (`_CartStepperButton` in `cart_stepper_button.dart`, `_CartShimmerRow` in `cart_shimmer_row.dart`), and the cart-screen verbs say what they change — `_incrementQuantity` / `_decrementQuantity` / `_confirmRemoveItem` / `_removeItem` / `_navToCheckout` on the ViewModel against `updateQuantity` / `removeItem` on the service.
- **Cart widgets are one class per file.** `lib/features/cart/widgets/` splits even the private helpers out — `cart_content.dart`, `cart_item_tile.dart`, `cart_quantity_stepper.dart`, `cart_stepper_button.dart`, `cart_remove_background.dart`, `cart_shimmer.dart`, `cart_shimmer_row.dart`, `cart_empty_view.dart`, `cart_summary.dart`. Privacy is per *library*, not per file, so a `_CartContent` in its own part file is still visible to the rest of the feature; every new file needs its `part` line in `cart_imports.dart`. The `checkout_*` widgets, in `lib/features/checkout/widgets/`, are looser — some carry a private helper class alongside the main one (`_MethodRow`, `_OptionRow`, `_ProductRow`, `_CardIconButton`), which is how they arrived and is left alone.
- **`updateCartItems` is not in the API brief** (which documents only add and remove) but the cart rows carry a stepper. Quantity 0 removes the line, which is what the minus button does on the last unit.
- **Checkout order is fixed by Magento**, not by preference: shipping address → shipping method → payment method → `placeOrder`. Methods are only quoted for a cart that already has an address, and a payment method is only accepted once a carrier is set. `CheckoutViewModel._selectAddress` therefore fires three calls behind one spinner (set shipping, set billing, re-quote). That ordering is also why the pager never lets a shopper skip ahead — see the checkout-flow bullets below.
- **`placeOrder` answers HTTP 200 with an `errors` list** when it refuses. `PlaceOrderResponse.isSuccess` — not the absence of a thrown exception — is what decides.
- **Adding to the cart requires an account**, and that is the only place the app asks. `CartService.addToCart` answers an anonymous tap with `AlertService.showConfirmation` — "Sign in to continue", Cancel or Confirm — and returns `false`; only Confirm pushes `RouteNames.login`, so the tap otherwise leaves the shopper where they were. It also shows its own error alert, so a caller only handles the success toast. Every screen with a cart icon is covered by that one method. Neither sign-in is privileged: `PrefKeys.isLoggedIn` is what counts. The per-SKU spinner is *not* shared — each product VM owns its own `_addingSkusCubit`, because the spinner belongs to the card that was tapped. Each screen's wrapper is still `_addToCart`.
- **A customer's cart is resolved, not minted.** With a token stored, `resolveCartId()` asks `customerCart` for the account's masked id (on a fresh install too, so the basket follows the account onto a new device); `createEmptyCart` is `ensureCartId()`'s fallback and the guest path, reached only by an add. `setGuestEmailOnCart` still fires when `PrefKeys.email` holds one, silently — it is what keeps the stubbed email/password login able to order at all, since it produces no token. Nothing gates the shipping step on it any more: if Magento still refuses, `placeOrder` says so in its own words on the review screen.
- **Any address can be deleted from the shipping step**, the default included — the first address saved is auto-flagged default, so hiding the button on it (as the card used to) meant a shopper with one address could never remove it. `_confirmDeleteAddress` asks first through `AlertService.showConfirmation`, the way the cart's remove does; `AddressBookService.remove` promotes a new default when the deleted one held the flag, and `_deleteAddress` re-selects it (clearing the selected id, the carrier and the quoted methods first) only when the deleted address was the selected one.
- **The address book is device-local** (`AddressBookService`, shared preferences). Magento's customer-address API is not part of this integration; the brief only exposes the two "set address on cart" mutations, which take a whole address inline. `region_id` is likewise not sent — there is no governorate table, and Magento resolves the `region` label on its own.
- Two places knowingly diverge from the payload: `ShippingMethodModel.displayTitle` uses `carrier_title` ("Best Way"), not `method_title` ("Table Rate"), because that is what the design shows; and the payment rows draw a code-derived icon rather than borrow an option's logo, because this store's `bankcards` options carry Instapay artwork.
- The map on the address form is `AddressFormLocationPicker`, a **placeholder** — a real picker needs `google_maps_flutter` and a platform API key, neither of which this project has. `AddressModel` already carries `latitude` / `longitude`, so wiring one in is a change to that widget alone.

**The cart-to-order cycle is two routes: the cart tab, then a three-page `PageView`.**

- **`CheckoutView` is the host, and the only View.** It (route `checkout`, top-level, beside `addressForm`) draws the `CustomAppBar` and the `CheckoutStepper` above a `PageView` held as a `late final _pages` **field** on the State, whose three children are `CheckoutShippingPage` / `CheckoutPaymentPage` / `CheckoutReviewPage` — one class per file in `widgets/`, each taking `vm`. The field is deliberate: the pager reads nothing from `_step`, so keeping one instance means a `setState` for the step never rebuilds the three page subtrees; they stay live because each is its own `BlocBuilder` on its own cubit. `view/checkout_view.dart` therefore holds **one** public class and nothing else: `CheckoutView` and its `_CheckoutViewState`, which own the step, the `PageController` and the app-bar/stepper chrome, and no page markup at all. None of the three pages carries a `Scaffold`, app bar or stepper of its own — each is just that step's `BlocBuilder` tree over the section widgets beside it. There are no `CheckoutShippingView` / `CheckoutPaymentView` / `CheckoutReviewView` classes, no `*Body` wrappers, and no `CheckoutPages` class. The app bar is now constant (`LocaleKeys.checkoutTitle` + a back arrow) and the stepper is always shown, so the `Column`'s child count is fixed and the earlier "keep the stepper slot occupied or the `Expanded` re-keys mid-animation" hazard is gone with it.
- **Nothing swipes.** The pager is `NeverScrollableScrollPhysics`. Forward moves only through a validated action — `_proceedFromShipping` once an address *and* a carrier are set, `_proceedFromPayment` once `setPaymentMethodOnCart` succeeds — and both reach the pager through the `_onProceed` callback that `_CheckoutViewState` injects into the VM (`CheckoutViewModel(onProceed: _forward)`), because the step lives in the State and the VM cannot call `setState`. Backward moves only through the host's back arrow or Android back, i.e. `_back()`. Free swiping would let a shopper reach payment with no address on the cart, where Magento quotes nothing.
- **Android back is `PopScope` between steps and a real pop at the edge.** The three pages are one route, so there is nothing to pop between them: the host sets `canPop: _step == CheckoutStep.address` and walks the pager back in `onPopInvokedWithResult`. On the first step it lets the pop through, which returns to the cart tab; `_back()` does the same thing for the app bar's arrow by calling `vm._exitCheckout()` there instead of animating.
- **There is no `CheckoutFlowService`, and the step is not a cubit.** `_CheckoutViewState` holds `CheckoutStep _step = CheckoutStep.address` and nothing else of substance: the `PageController` is the VM's, and so is the animation. The View's `_goTo(index)` bounds-checks, `setState`s the new step, then calls `vm._goToStep(step)`, which loads that step and animates the pager. `setState` before the animation is what makes the app bar and stepper flip immediately, and `_onPageChanged` only catches up at the settle (it early-returns when the step already matches, so it never double-fires). The step stays in the State because it is `setState` layout state that nothing else reads; everything the View is not allowed to own went to the VM — `_init()` / `_dispose()`, the controller, the animation's duration and curve, and the route pop (`_exitCheckout()`), so the View holds no service and no controller at all. The step is plain `setState` state precisely because nothing outside this State reads it — the earlier `GenericCubit<int>` on a service existed **only** so the shell's sibling `bottomNavigationBar` could hide itself, and making checkout a top-level route removed that reader. `CheckoutStep` (from `core/widgets/checkout_stepper.dart`) doubles as the step type, so `step.index` *is* the page index and no separate `0..3` constants exist. The address choice is likewise plain per-flow state now: `_selectedAddressIdCubit` on the VM is the only record of it, since the VM outlives all three steps and dies with the route.
- **`attach` / `detach` emit their step reset in a post-frame callback.** A step change repaints `LayoutShellView`'s bottom bar, and the host mounts and unmounts *during* a build, so emitting straight from `attach` / `detach` would be a `markNeedsBuild` during build. The reset itself is not optional: an edge-swiped drawer is reachable from a checkout page, and leaving the step on `paymentStep` after the host is gone would hide the bottom bar with no way to bring it back.
- **A step's refetch is explicit, because the pages have no lifecycle of their own.** They are `StatelessWidget`s under a State that never unmounts mid-flow, so there is no `initState` to hang a load on: `vm._goToStep(step)` calls `_loadStep(step)` **before** animating, and `vm._init()` calls it for the first step. That switch is the single place step data is fetched — `address` to `_loadShipping()`, `payment` to `_loadPayment()`, `review` to `_cartService.loadCart()` — and being exhaustive over the enum, adding a step is a compile error until it is handled. Loading before the animation (rather than from `_onPageChanged`, which fires after it) keeps the incoming page from flashing empty. Landing on a step therefore re-quotes shipping and re-fetches payment methods every time, forward or backward. `_loadShipping` clears `_shippingErrorMessage` on entry and prefers `_rememberedAddress()` (the VM's own `_selectedAddressIdCubit`) over `_addressBookService.defaultAddress`, so stepping back to shipping keeps the shopper's non-default address instead of silently reverting to the default. The cart tab is separate and loads itself: `CartView.initState` -> `vm._init()` -> `loadCart()`.
- **Leaving the flow needs no cleanup.** The whole flow is one route's State, so popping or replacing it discards the step, the `PageController`, the quoted methods and the selected address together; a later visit is a fresh `CheckoutView` on step one. `_placeOrder` just `clearCart()`s and `goNamed(orderConfirmed)` — that `go` replaces the location, so the checkout route comes off the stack and the shell (with its bottom bar) is what the confirmation renders in. `AppStartupService.logout()` no longer has a flow to reset.

### Persistence

- `SharedPrefsServices` — static wrapper over `shared_preferences`, `init()`ed in `main()`; keys in `pref_keys.dart`. Drives the splash gate (`isFirstTime` / `isLoggedIn`) via `SplashViewModel.checkAppStart/saveLoggedIn/logout`, and caches profile fields.
- `DbServices` — sqflite store behind the wishlist (`favorites` table) and the notify-me subscriptions, registered in the locator and reached with `sl<DbServices>()` from `FavoritesService` and `PushNotificationService`. `FavoritesService` publishes it as a `GenericCubit<ListFavorites>` plus a `loadingCubit`; `isFavorite(sku)` is a service method the favourite buttons call from inside their builder.

### Localization & UI conventions

- `easy_localization` with `assets/translations/{ar,en}.json`; `startLocale` is Arabic, fallback English. Reference strings via `LocaleKeys.someKey.tr()` — add the constant to `lib/core/localization/locale_keys.dart` **and** both JSON files. (Some validation/API error messages are still hardcoded Arabic literals — most of them in `AuthSessionService`.)
- `flutter_screenutil` with `designSize: Size(430, 932)` — size text with `.sp`, dimensions with `.w` / `.h` / `.r`.
- Shared constants in `lib/core/constants/` (`AppColors`, `AppSizes`, `AppImages`); shared widgets in `lib/core/widgets/` (`AppButton`, `AppTextField`, `AuthHeader`); form validation helpers in `lib/core/utils/validators.dart`.
